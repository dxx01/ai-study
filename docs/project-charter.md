# 项目说明书（Project Charter）

> 最后更新：2026-10-25 · 状态：v0.5 开发中
> 本文回答三个问题：**为谁解决什么问题、做到什么程度算完成、哪些事不做**。
> 任务清单看 [roadmap.md](roadmap.md)；启动方式看 [README.md](../README.md)。

## 0. 一句话定位

**一个“有据可查”的居家营养与健康科普助手**：把用户上传或内置的资料变成带引用的回答；资料不足时明确说不知道，而不是编。

它不是通用聊天壳，也不是医疗诊断工具。核心差异只有两个字：**可追溯**。

## 1. 为什么做

- 健康信息过载，来源质量参差；通用大模型容易“一本正经地编”。
- 用户真正需要的是：**这句话依据哪份资料**，以及**什么时候该去看医生**。
- 对作者而言，它同时是一个学习载体：把 RAG、评测、流式、工具调用这些 AI 工程能力，落在一条能跑通的业务链上，而不是散落的 demo。

## 2. 目标用户与场景

| 角色 | 需求 | 不负责 |
|------|------|--------|
| 普通用户 | 问膳食、运动、常见症状的科普问题；上传自己的资料后提问 | 诊断、处方、病历解读 |
| 内容维护者 | 上传/整理知识库文档，确认索引成功 | 复杂的 CMS、审批流 |

三个典型任务：

1. **资料内问答**：上传一份膳食指南，问“高血压人群的食盐建议是什么”，回答必须引用该文档。
2. **资料外问题**：问知识库没有的内容，回答应说明依据不足，并给出就医/权威渠道建议。
3. **时效性问题**：问“今年有什么新研究”，在配置联网检索时给出带来源的摘要，并标注“联网检索”。

## 3. 用户旅程（同时是验收脚本）

| # | 旅程 | 通过标准 |
|---|------|----------|
| 1 | 打开 → 登录 → 看到专家介绍 → 问“你好” | 3 秒内进入对话；回答有免责声明 |
| 2 | 上传 PDF/Word → 列表出现文档 → 问文档内问题 | 回答引用正确文档名与片段 |
| 3 | 问知识库外的问题 | 明确说“资料不足/建议就医”，不编造来源 |
| 4 | 配置 Tavily 后问时效性问题 | 出现“联网检索”来源；失败时降级而不是 500 |
| 5 | 同一会话连续追问 | 历史生效，且不串到别人的会话 |

任何新功能，至少服务其中一条旅程；否则不进当前迭代。

## 4. 范围

### 4.1 v0.5（当前迭代，必须完成）

- 登录/注册、单专家对话
- 流式输出（SSE）+ 前端逐字渲染
- 知识库上传、列表、检索；本地引用展示
- 资料不足时的拒答与免责声明
- 一条命令起基础设施；五个服务 + 前端可启动
- **20–30 条金标评测集 + 指标脚本**
- README 的四步冒烟全部通过

### 4.2 v1.0（v0.5 稳定后再做）

- 中文 embedding（bge-small-zh 或 embedding API）+ rerank + 引用对齐
- 向量库持久化（PGVector/Milvus）；知识库元数据落 MySQL
- 会话历史页、会话管理
- token/成本/延迟可观测；限流与配额
- 输入输出护栏、PII 脱敏、prompt injection 防护
- Tool calling 替代正则 AUTO

### 4.3 非目标（明确不做）

- ❌ 诊断、处方、病历、医保结算
- ❌ 通用 Agent 平台 / 插件市场
- ❌ 多租户 SaaS、计费、组织权限后台
- ❌ 模型训练/微调
- ❌ 移动端原生 App、实时音视频
- ❌ 为“看起来更 AI”而堆功能（多模型路由、花哨 UI 等）

## 5. 成功指标

### AI 质量（v0.5 基线，v1.0 提升）

| 指标 | v0.5 目标 | 测量方式 |
|------|-----------|----------|
| 检索 recall@5 | ≥ 0.8 | 金标问题标注应命中的文档/片段 |
| 引用命中率 | ≥ 0.8 | 回答引用的文档是否包含答案 |
| groundedness | ≥ 0.9 | 抽样人工/LLM judge：每句是否有依据 |
| 拒答正确率 | ≥ 0.9 | 资料外问题是否明确说不知道 |
| 幻觉率 | < 5% | 编造来源/结论的比例 |
| 首 token 延迟 | < 2s | 前端/网关埋点 |
| P95 完整回答 | < 10s | 同上 |

## 6. 设计原则（防止跑偏）

1. **证据优先**：没有检索依据就明说；引用必须来自本次检索，不能事后补。
2. **可评测**：任何 AI 改动先有基线，再看指标；不接受“感觉更好”。
3. **可降级**：知识库/联网/模型故障时给明确提示，不把 500 抛给用户。
4. **边界清晰**：编排在 `ai-service-llm`，检索在 `ai-service-knowledge`，持久化在 `ai-service-conversation`，网关只做路由与登录校验。
5. **数据最小化**：只存回答必需的数据；密钥按服务最小化（模型 Key 只在 `ai-service-llm`，embedding Key 只在 `ai-service-knowledge`）。
6. **一次只改一个变量**：embedding、chunk、topK、rerank、prompt 分开验证。
7. **不为演示加功能**：新功能必须映射到第 3 节的旅程与第 5 节的指标。

## 7. 架构与选型（为什么，以及代价）

| 选择 | 理由 | 代价 |
|------|------|------|
| Spring Boot 3.4 + Spring AI 1.0 | Java 生态成熟；ChatClient/Advisor/VectorStore 抽象清晰 | 版本较新，资料以官方文档为主 |
| 微服务拆分 | 学习服务边界与独立部署 | 本地要起 5 个进程，运维复杂 |
| MySQL + MyBatis-Plus | 用户/会话事务清晰，审计字段好做 | 手工 DDL，改表要同步脚本/实体/文档 |
| Redis + Sa-Token | 无状态网关 + 集中会话 | 多一个基础设施依赖 |
| `SimpleVectorStore`（当前） | 零依赖，先把链路跑通 | 内存态、重启重建，v1.0 必须换 |
| transformers ONNX embedding（当前） | 不依赖外部 embedding API | 首次下载模型；默认模型偏英文 |
| Vue 3 + Element Plus | 快速做可用界面 | 组件风格较重，后续可换轻量方案 |
| 手工 DDL（当前） | 前期简单、可审计 | 多人协作/多环境时易漂移，稳定后再评估 Flyway |

## 11. 术语

| 术语 | 含义 |
|------|------|
| RAG | 检索增强生成：先检索资料，再让模型基于资料回答 |
| chunk | 文档切分后的片段，是检索与引用的最小单位 |
| embedding | 把文本映射成向量，用于相似度检索 |
| rerank | 对召回结果做二次精排，提高引用准确率 |
| groundedness | 回答是否有检索依据支撑 |
| tool calling | 让模型决定调用哪个工具（检索/联网等） |
| SSE | Server-Sent Events，流式返回 |
| eval | 用固定问题集与指标衡量 AI 改动效果 |
