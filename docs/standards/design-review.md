# 方案设计与建议审查（通用清单）

> 适用于任意项目的**讨论 / 建议 / 方案**模式。Agent 触发后先按本文审查，再读取**当前仓库**的项目补强（见下文 §6）。  
> 触发约定：以 [AGENTS.md](../../AGENTS.md) 的「方案 / 建议模式」为准；Cursor 侧由 `.cursor/rules/agent-communication.mdc` 适配。

## 1. 原则

- **目标优先**：本期要解决什么、明确不做什么。
- **现状优先**：复用已有架构与规范，避免平行体系。
- **适度设计**：识别未来可能需要的实体，不等于本期全部实现。
- **事实与假设分离**：未读代码/配置/库表时标明「待核实」。

## 2. 方案前快速扫描

1. 问题与边界：用户目标、约束、本期范围。  
2. 现有基础：已实现能力、可复用模块、真实缺口。  
3. 核心对象：是否应建模为实体/配置中心，而非散落字段或前端常量。  
4. 生命周期：创建、使用、修改、停用、删除；关联数据如何处理。  
5. 关系：一对一 / 一对多 / 多对多，是否会演变。  
6. 权限与归属：谁可读写的资源；是否需要所有权与租户/应用隔离。

## 3. 反向审查维度

| 维度 | 自问 |
|------|------|
| 完整性 | 是否只改单点、漏实体/接口/任务/迁移？ |
| 安全 | 越权、数据泄漏、上传、密钥、审计、默认暴露？ |
| 兼容 | 破坏现有 API/数据/客户端？迁移与回滚？ |
| 扩展 | 配置硬编码位置、可替换实现边界？ |
| 性能 | 数据量、索引、分页、并发、缓存、超时？ |
| 可靠性 | 幂等、事务、重试、降级、外部依赖不可用？ |
| 可维护 | 分层、重复逻辑、观测与排障？ |
| 成本与交付 | 更简单方案？分期？范围蔓延？ |
| 验收 | 正常/异常/权限/迁移如何判定通过？ |

## 4. 完整性复核（架构 / 库表 / 跨模块时必做）

1. 是否把应独立管理的对象压成字段或常量？  
2. 关系是否需要关联表、状态或注册表？  
3. 业务链路是否闭环？  
4. 前后端、存储、第三方职责是否清晰？  
5. 是否存在结构更优或长期成本更低的替代方案？  
6. 缺口中哪些必须现在解决，哪些仅文档预留？

## 5. 输出分期（每次方案建议应标明）

- **本期必须**：不做则目标失败、安全不成立或返工成本过高。  
- **建议预留**：扩展点/字段/接口，不建完整子系统。  
- **暂不实现**：无明确需求、收益不足或超出项目非目标。

输出格式按复杂度裁剪：简单问题可「结论 + 少量风险」；中等问题用「现状 → 推荐 → 备选 → 审查摘要 → 分期 → 验收」。

## 6. 识别项目后的补强（在通用清单之上）

进入方案模式后，Agent **应先判断当前仓库类型**，再阅读对应补强文档（若存在）：

| 若当前仓库是… | 补强文档（事实来源） |
|---------------|----------------------|
| **本仓库 ai-study** | [design-review-ai-study.md](design-review-ai-study.md)、[AGENTS.md](../../AGENTS.md)、[project-charter.md](../project-charter.md) |
| 其他项目 | 该项目的 `AGENTS.md` / `README` / 架构说明；无则仅通用清单 + 用户口述约束 |

补强内容只**叠加**检查项，不替代 §2–§5 的通用维度。
